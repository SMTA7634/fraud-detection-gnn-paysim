Section 3a — Account node feature vector (10 dims)

What each account node "knows"

out_degree outgoing How many transactions this account SENT
out_total_log outgoing log1p(total $ sent). Large = big sender
out_avg_log outgoing log1p(avg $ per outgoing txn)
out_drain_frac outgoing Fraction where pct_balance_used ≥ 0.99 — account fully drained. Fraud = 1.0 always
out_transfer_frac outgoing Fraction of outgoing that are TRANSFER or CASH_OUT — the only types with fraud
in_degree incoming How many transactions this account RECEIVED
in_total_log incoming log1p(total $ received). High = mule account
in_distinct_senders incoming Unique senders to this account. Many fraud senders → high = suspicious recipient
total_degree combined out + in. Overall activity level
out_in_ratio combined out ÷ total. 1.0 = only sends, never receives. Fraud accounts often = 1.0

All 10 features are StandardScaler-normalised using training-account statistics only, then applied to all 462k accounts.

Key insight: Model 4 answers a different question than Models 1–3. Transaction-level models (1–3) block a payment before it moves. Account-level Model 4 scores whether an account is a fraudster — used for overnight account suspension, KYC risk tiers, or fraud ring investigation. Both are needed in a real fraud system.
Leakage note (for interviews): Model 4's node features are aggregated over ALL transactions, including those after the OOT cutoff — technically leaky. In production you'd use an event-time feature store: compute each account's features up to the moment of scoring, not beyond it. Always mention this trade-off when presenting this model.
